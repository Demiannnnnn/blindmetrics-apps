# Security Model

## 1. Keys and secrets

| Secret / value | Generated by | Stored | Lifetime | Leaves the machine? |
|:---------------|:-------------|:-------|:---------|:--------------------|
| `K_admin_priv` (X25519) | Admin app, first run | OS keystore `TelemetryAdminVault` / `admin_master_key_v1`; optional `.vault` backup (Argon2id + AES-256-GCM) | Forever (no rotation, see §6) | Never (only as encrypted backup file the admin controls) |
| `K_admin_pub` | Derived | Server (`admins.public_key`, write-once); pinned in every agent | Forever | Yes (public) |
| Ephemeral X25519 pair | Agent, **per envelope** | RAM only, zeroized after use | One envelope | Only the public half, inside the record |
| Shared secret, DEK | Both sides | RAM, `Zeroizing` | One envelope | Never |
| Admin access token | Server | Admin Rust RAM | 15 min | Only to the API |
| Admin refresh token | Server | OS keystore `TelemetryAdminVault` / `admin_refresh_token` | 7 days, single-use rotation | Only to the API |
| Worker access/refresh tokens | Server (at enrollment and refresh) | OS keystore `TelemetryWorker` / `access_token`, `refresh_token` | 15 min / 7 days rotating | Only to the API |
| Enrollment code | Server | Server stores SHA-256 only; admin UI shows once | Single use, ≤ 24 h (max 72) | Physical channel (QR / reading it out) |

## 2. Envelope encryption (implemented)

```
Agent (per category, per flush):
  (k_eph, K_eph) ← X25519 keygen (OsRng)
  ss   ← X25519(k_eph, K_admin_pub_pinned)
  dek  ← HKDF-SHA256(ikm = ss, salt = "telemetry-v1", info = "aes256gcm") → 32 bytes
  nonce← 12 random bytes
  ct‖tag ← AES-256-GCM(dek, nonce, plaintext = JSON(PlaintextBatch))
  encrypted_payload = nonce ‖ tag ‖ ct          (min 28 bytes)
  zeroize(k_eph, ss, dek)
  send { ephemeral_public_key = b64(K_eph), encrypted_payload = b64(...) }

Admin:
  ss  ← X25519(K_admin_priv, K_eph);  dek ← HKDF(...);  pt ← AES-GCM-Open(...)
  check pt.worker_id == record.worker_id && pt.category == record category   (SEC-09)
```

`PlaintextBatch` binds `worker_id` and `category` inside the ciphertext so a malicious server cannot move a record between workers or categories undetected. Schema: `docs/telemetry-payloads.md`.

## 3. Enrollment integrity (TASK-CRYPTO-02 / ADMIN-08 / AGENT-08)

TLS protects against the network, **not against the server**. A compromised server could hand the agent its own public key (key substitution) and read everything. Defence: the admin app computes a commitment over what the worker must receive and sends it over the physical channel.

### 3.1 Canonical manifest

Implemented once in `telemetry_crypto_core::enrollment`. Serialized with `serde_json::to_vec` (compact, no whitespace) from this struct — **field order is part of the format**:

```rust
#[derive(Serialize)]
pub struct EnrollmentManifest {
    pub v: u8,                                   // 1
    pub admin_public_key: String,                // standard base64, 44 chars
    pub consent_version: i32,
    pub consent_flags: CanonicalFlags,           // all 6 bools, fixed order below
    pub consent_descriptions: CanonicalDescriptions, // all 6 keys, fixed order, Option<String>
}
// fixed order: system_activity, network_activity, productivity_basic,
//              productivity_screenshots, file_activity, location
```

Normalization before hashing: a description whose flag is `false` is set to `None`; descriptions are used byte-exact as returned by the server (the admin app trims before sending).

```
commitment  = SHA-256( b"telemetry-enroll-v1\0" ‖ canonical_json )     → 64 hex
safety_code = u64_be(commitment[0..8]) mod 10^12, zero-padded, "dddd dddd dddd"
fingerprint = hex(SHA-256(raw 32-byte K_admin_pub))                    (same as server)
manifest_hash (sent in PATCH /consent) = commitment of the manifest the worker accepted
```

### 3.2 Flow

1. Admin app creates the worker, gets `{ worker, enrollment.code }`.
2. Admin app builds the manifest **from the server response** (`consent_version`, requested flags, descriptions) plus its **own locally derived** `K_admin_pub` (from the keystore, not from the server), and checks the response flags/descriptions equal what it sent. Mismatch ⇒ error, no QR.
3. QR = `{"t":"telemetry-enroll","v":1,"api_url":…,"code":…,"commitment":…}`. The screen also shows the code and safety code.
4. Agent redeems the code, builds the manifest from the response, recomputes the commitment:
   - QR path: must equal `qr.commitment`, else abort + wipe + "possible tampering" screen.
   - Manual path: shows the safety code; the worker confirms it matches the admin's screen ("They match" / "They don't match"). No match ⇒ abort + wipe.
5. Agent pins `K_admin_pub`, its fingerprint and the accepted `manifest_hash`.

### 3.3 After enrollment

- `GET /workers/me` returns `admin_public_key_fingerprint`; if ≠ pinned ⇒ `Halted` (SEC-08).
- New consent versions arrive from the server **unsigned** (known gap). The worker still has to accept them on screen, so they cannot be applied silently, but their origin is not authenticated. Phase 2: admin Ed25519 signing key, whose fingerprint joins the manifest; the agent rejects unsigned updates.

## 4. Threat model (summary)

| Threat | Mitigation | Residual |
|:-------|:-----------|:---------|
| DB dump | Ciphertext only; enrollment codes and refresh tokens hashed. | Metadata (timestamps, sizes, categories) visible. |
| Malicious/compromised server substitutes key | Commitment + pinning. | Manual-code path relies on the worker actually comparing the safety code. |
| Server moves records between workers | `worker_id`/`category` inside ciphertext, checked by the admin. | Server can drop or replay records (detectable only by gaps/duplicates). |
| Stolen enrollment code | Single use, 24 h, admin sees `device_info` and can revoke + re-issue. | Attacker wins the race if faster than the employee. |
| Stolen worker laptop | Tokens in OS keystore; admin revokes. Queue is ciphertext. | Attacker with the OS session can inject fake telemetry until revoked. |
| XSS in admin WebView | No tokens/keys in JS; CSP `default-src 'self'`; decrypted data only in memory. | XSS could read decrypted data currently on screen. |
| Admin loses `K_admin_priv` | Encrypted backup export (first-run wizard nags until done). | Without backup, history is unrecoverable by design. |

## 5. Local storage rules

- `config.json` holds **no** secrets. If you are about to add a field with "token", "key" or "secret" in its name to a serialized config struct, stop.
- The offline queue holds only envelopes (already encrypted) and their category/timestamp.
- Logs: never payloads, tokens, codes, keys, window titles or FQDNs at `info` or above; `debug` may include counts and categories only.

## 6. Out of scope

- `K_admin_pub` rotation (would require re-enrolling every agent and makes history undecryptable without the old key).
- Multi-admin organizations sharing one key.
- Code signing / notarization pipelines (tracked in release tasks, not here).
