# Security Model

## 1. Keys and secrets

| Secret / value | Generated by | Stored | Lifetime | Leaves the machine? |
|:---------------|:-------------|:-------|:---------|:--------------------|
| `K_admin_priv` (X25519) | Admin app, first run (or the web portal onboarding) | OS keystore `TelemetryAdminVault` / `admin_master_key_v1`; `.tkb` backup file and/or server vault (Argon2id + AES-256-GCM, §4) | Until a destructive rotation (§4.4) | Never in clear (only as encrypted backup) |
| Master Password | The admin | Nowhere (typed when needed); `Zeroizing<String>` while in use | — | Never |
| KEK | `Argon2id(Master Password, salt)` on the client | RAM only, `Zeroizing` | One backup/restore operation | Never |
| Admin device id | Admin app, first login | OS keystore `TelemetryAdminVault` / `admin_device_id` (`inst-<uuid>`) | Installation | Only to the API (device descriptor) |
| `K_admin_pub` | Derived | Server (`admins.public_key`, write-once); pinned in every agent | Forever | Yes (public) |
| Ephemeral X25519 pair | Agent, **per envelope** | RAM only, zeroized after use | One envelope | Only the public half, inside the record |
| Shared secret, DEK | Both sides | RAM, `Zeroizing` | One envelope | Never |
| Admin access token | Server | Admin Rust RAM | 15 min | Only to the API |
| Admin refresh token | Server (bound to the admin device) | OS keystore `TelemetryAdminVault` / `admin_refresh_token` | 7 days, single-use rotation, family revoked on reuse | Only to the API |
| Worker access/refresh tokens | Server (at enrollment and refresh) | OS keystore `TelemetryWorker` / `access_token`, `refresh_token` | 15 min / 7 days rotating | Only to the API |
| Enrollment code | Server | Server stores SHA-256 only; admin UI shows once | Single use, 1–72 h (default 24) | Physical channel (QR / reading it out) |
| Google `code`, PKCE verifier, `state`, `nonce`, ID token | Admin app / Google | RAM only (`Zeroizing`) | One sign-in (≤ 180 s) | ID token only to the API |

## 2. Envelope encryption (implemented)

```
Agent (per category, per flush):
  (k_eph, K_eph) ← X25519 keygen (OsRng)
  ss   ← X25519(k_eph, K_admin_pub_pinned)
  dek  ← HKDF-SHA256(ikm = ss, salt = "telemetry-v1", info = "aes256gcm") → 32 bytes
  nonce← 12 random bytes
  ct‖tag ← AES-256-GCM(dek, nonce, plaintext = JSON(PlaintextBatch))
  encrypted_payload = nonce ‖ tag ‖ ct          (min 28 bytes)
  zeroize(k_eph, ss, dek)
  send { ephemeral_public_key = b64(K_eph), encrypted_payload = b64(...) }

Admin:
  ss  ← X25519(K_admin_priv, K_eph);  dek ← HKDF(...);  pt ← AES-GCM-Open(...)
  check pt.worker_id == record.worker_id && pt.category == record category   (SEC-09)
```

`PlaintextBatch` binds `worker_id` and `category` inside the ciphertext so a malicious server cannot move a record between workers or categories undetected. Schema: `docs/telemetry-payloads.md`.

## 3. Enrollment integrity (TASK-CRYPTO-02 / ADMIN-08 / AGENT-08)

TLS protects against the network, **not against the server**. A compromised server could hand the agent its own public key (key substitution) and read everything. Defence: the admin app computes a commitment over what the worker must receive and sends it over the physical channel.

### 3.1 Canonical manifest

Implemented once in `telemetry_crypto_core::enrollment`. Serialized with `serde_json::to_vec` (compact, no whitespace) from this struct — **field order is part of the format**:

```rust
#[derive(Serialize)]
pub struct EnrollmentManifest {
    pub v: u8,                                   // 1
    pub admin_public_key: String,                // standard base64, 44 chars
    pub consent_version: i32,
    pub consent_flags: CanonicalFlags,           // all 6 bools, fixed order below
    pub consent_descriptions: CanonicalDescriptions, // all 6 keys, fixed order, Option<String>
}
// fixed order: system_activity, network_activity, productivity_basic,
//              productivity_screenshots, file_activity, location
```

Normalization before hashing: a description whose flag is `false` is set to `None`; descriptions are used byte-exact as returned by the server (the admin app trims before sending).

```
commitment  = SHA-256( b"telemetry-enroll-v1\0" ‖ canonical_json )     → 64 hex
safety_code = u64_be(commitment[0..8]) mod 10^12, zero-padded, "dddd dddd dddd"
fingerprint = hex(SHA-256(raw 32-byte K_admin_pub))                    (same as server)
manifest_hash (sent in PATCH /workers/me/consent) = commitment of the full manifest shown to the worker
```

### 3.2 Flow

1. Admin app creates the worker (or regenerates the code), gets `{ worker, enrollment: { code, expires_at, commitment, safety_code, qr_payload } }`.
2. Admin app builds the manifest **from the server response** (`consent_version`, requested flags, descriptions) plus its **own locally derived** `K_admin_pub` (from the keystore, not from the server), and checks the response flags/descriptions equal what it sent. It recomputes the commitment and safety code and compares them with the server's, and decodes `qr_payload` to check `code` and `commitment`. Any mismatch ⇒ `ENROLLMENT_INTEGRITY_ERROR`, no QR (ADMIN-09). The server's values are never trusted on their own: a compromised server would compute them over its own key.
3. QR = `qr_payload` = base64 of `{"t":"telemetry-enroll","v":1,"api_url":…,"code":…,"commitment":…}` (the agent also accepts the raw JSON). The screen also shows the code, the safety code and the server host.
4. Agent redeems the code, builds the manifest from the response, recomputes the commitment:
   - QR path: must equal `qr.commitment`, else abort + wipe + "possible tampering" screen.
   - Manual path: shows the safety code; the worker confirms it matches the admin's screen ("They match" / "They don't match"). No match ⇒ abort + wipe.
5. Agent pins `K_admin_pub` and its fingerprint. After the worker chooses categories, it stores the accepted `manifest_hash` and the accepted selection.

### 3.3 After enrollment

- `GET /workers/me` returns `admin_public_key_fingerprint`; if ≠ pinned ⇒ `Halted` (SEC-08).
- New consent versions arrive from the server **unsigned** (known gap). The worker still has to accept them on screen, so they cannot be applied silently, but their origin is not authenticated. Phase 2: admin Ed25519 signing key, whose fingerprint joins the manifest; the agent rejects unsigned updates.

## 4. Admin key backup and recovery (TASK-CRYPTO-03 / ADMIN-11)

### 4.1 Format v2 (`.tkb` and server vault)

```
salt   ← 16 random bytes
KEK    ← Argon2id(v=19, m=65536 KiB, t=3, p=4, password = Master Password, salt) → 32 bytes
nonce  ← 12 random bytes
ct‖tag ← AES-256-GCM(KEK, nonce, plaintext = raw 32-byte K_admin_priv, AAD = "telemetry-key-backup-v2")
encrypted_private_key = b64(nonce ‖ tag ‖ ct)                       (60 bytes)
zeroize(KEK, Master Password, K_admin_priv copies)
```

Accepted parameter ranges (client and server): m 32 768–1 048 576 KiB, t 2–20, p 1–16, salt
16–64 bytes. Parameters are validated **before** deriving (a malicious file or server cannot force
huge memory). After decrypting, the key must derive the fingerprint recorded in the container and
the one registered on the server.

### 4.2 What the server sees

`encrypted_private_key`, `argon2_params` and the public key fingerprint. Never the Master Password,
never the key in clear, never Argon2 execution. Every download of the backup is audited
(`VAULT_BACKUP_ACCESSED`).

### 4.3 Flows

| Flow | Steps |
|:-----|:------|
| Export `.tkb` | Verify the Master Password (decrypt the server backup if one exists; otherwise type it twice) → fresh salt + nonce → write `telemetry_key_{org}_{date}.tkb` (0600, never overwrite). |
| Server backup | Encrypt locally → `POST /admins/me/vault/setup` (closed DTO). |
| Restore (A: file, B: server) | Validate params → decrypt → fingerprint = registered key → keystore → device fingerprint `PATCH`. |
| New key (C) | Double confirmation in Rust → keystore (old key kept in RAM) → rotate on server → rollback on failure. |

### 4.4 Rotation

`POST /admins/me/public-key/rotate` replaces the registered key, **revokes every worker** (they must
re-enroll and pin the new key), deletes the server backup and forgets device fingerprints. Data
encrypted to the old key stays readable only with the old private key. The app offers to export the
old key before replacing it.

## 5. Sessions, devices and sign-in

- **Single-flight refresh** in both apps (SEC-14): concurrent refreshes with the same token look like a
  replay to the server, which revokes the whole family.
- **Admin devices:** login/register/Google send `device { fingerprint = installation id, name, public_key_fingerprint }`;
  the JWT carries `did`. Revoking a device from another session makes its access tokens fail with
  `401 DEVICE_REVOKED` immediately.
- **Google on desktop** (SEC-16): system browser + loopback `127.0.0.1:<random port>` + PKCE S256 +
  `state` + `nonce`. The API verifies the ID token signature (Google JWKS), `aud` (includes the
  desktop client id), `iss`, `exp` and `email_verified`; the app only checks `nonce`. The Google
  "Desktop app" client secret is not confidential by design (installed-app flow).
- **Billing portal**: the URL comes from the server and is validated before opening (SEC-17).

## 6. Threat model (summary)

| Threat | Mitigation | Residual |
|:-------|:-----------|:---------|
| DB dump | Ciphertext only; enrollment codes and refresh tokens hashed; key backup encrypted with Argon2id-derived KEK. | Metadata (timestamps, sizes, categories) visible; offline guessing of weak Master Passwords (≥ 12 chars + Argon2id 64 MiB/t=3 make it expensive). |
| Malicious/compromised server substitutes key | Commitment computed with the admin's **local** key + pinning in the agent. | Manual-code path relies on the worker actually comparing the safety code. |
| Malicious server tampers the key backup | AEAD tag + AAD; fingerprint check against the registered key; params validated before derivation. | Server can delete the backup (the `.tkb` file is the independent copy). |
| Server moves records between workers | `worker_id`/`category` inside ciphertext, checked by the admin. | Server can drop or replay records (detectable only by gaps/duplicates). |
| Stolen enrollment code | Single use, 1–72 h, 3 failures/15 min lockout per IP, admin sees `device_info` and can revoke + re-issue. | Attacker wins the race if faster than the employee. |
| Stolen `.tkb` file | Useless without the Master Password; Argon2id makes guessing slow. | Weak Master Password. |
| Lost/stolen admin laptop | Revoke the device from another session (tokens die at once); key in the OS keystore behind the OS account. | Attacker with the unlocked OS session. |
| Stolen worker laptop | Tokens in OS keystore; admin revokes. Queue is ciphertext. | Attacker with the OS session can inject fake telemetry until revoked. |
| Concurrent refresh / token replay | Single-flight refresh; family revocation on reuse. | A stolen refresh token works until its legitimate owner refreshes (then both are revoked). |
| Someone at an unattended, auto-locked admin machine | Auto-lock purges decrypted data and drops the access token; password unlock with revocation after 5 failures. | **Open gap:** the "Biometría" unlock button re-opens the session with the stored refresh token without any OS verification. Fix: call the OS authenticator (macOS LocalAuthentication, Windows Hello) before `unlock_with_refresh`, or remove the button. |
| XSS in admin WebView | No tokens/keys in JS; CSP (`tauri.conf.json`) `default-src 'self'` — so the WebView cannot `fetch` external hosts (`connect-src` falls back to `'self'`); `img-src` also allows `https:`/`data:`/`blob:` for map tiles and QR PNGs; URLs to open come from Rust (`open_billing_portal` uses only the server's `portal_url`); decrypted data only in memory. | XSS could read decrypted data currently on screen or a password being typed. **Known gap:** `script-src` still allows `'unsafe-inline'` and `'unsafe-eval'`; tightening it (hashes/nonces, no eval) is pending hardening work. |
| Admin loses `K_admin_priv` | `.tkb` + server vault; recovery screen on every new device. | Without backup (or without the Master Password), history is unrecoverable by design. |
| Subscription lapses | Server blocks; admin lock screen; agent keeps queued ciphertext (7 days). | Data older than the queue retention is not collected during the suspension (minimization by design). |

## 7. Local storage rules

- `config.json` holds **no** secrets. If you are about to add a field with "token", "key" or "secret" in its name to a serialized config struct, stop.
- The offline queue holds only envelopes (already encrypted) and their category/timestamp.
- `.tkb` files are written by the admin app with permissions `0600` and never overwrite an existing file.
- Logs: never payloads, tokens, codes, keys, passwords, window titles or FQDNs at `info` or above; `debug` may include counts and categories only.

## 8. Out of scope

- Multi-admin organizations sharing one key.
- Non-destructive key rotation (re-encrypting history or keeping several active keys).
- Code signing / notarization pipelines (tracked in release tasks, not here).

## 9. Attendance data (contract v3, AGENT-10..13, ADMIN-13..16)

### 9.1 Why it is not zero-knowledge

R38 requires the server to email a receipt per mark, verify marks by hash on a public page, compute
reports and give labour inspectors permanent read access (`docs/legal/marco-legal-cl.md` §1). The
server therefore stores attendance **in plaintext**. Mitigations: attendance contains no telemetry and
no secrets (SEC-21); minimal fields (R38 art. 13); access by role with audit (admin, worker, inspector,
read-only third parties); 5-year retention then destruction; extra personal data destroyed 90–120
days after the employment ends.

The admin's X25519 key is **not** used for attendance. Losing it does not affect attendance.

### 9.2 Identification: PIN on the enrolled device

```
set/change:  pin (Zeroizing) ── policy check (SEC-20) ── Argon2id(m=19 MiB, t=2, p=1, salt 16B) ──> verifier
             verifier → OS keystore TelemetryWorker/pin_verifier ; POST /workers/me/credential-events {PIN_SET|PIN_CHANGED}
mark:        UI ──(IPC, Zeroizing)──> service ── verify (constant time) ── ok ⇒ mark ; fail ⇒ delay 2^n s (max 60 s)
reset:       POST /workers/me/pin-reset/request → code to personal email (10 min, 5 tries)
             POST /workers/me/pin-reset/verify { code } → 204 ⇒ UI asks new PIN ⇒ set
```

- The PIN never reaches the server. The server learns only the events (for the R38 art. 7 f email).
- Lighter Argon2 parameters than the key backup: the PIN is entered several times a day; the verifier
  lives in the OS keystore (not on disk), so offline guessing needs the OS account first.
- The worker JWT authenticates the device; the PIN proves the person at the device. Together they are
  the **primary** identification. The **secondary** one (R38 art. 7 g) is the worker login of the web
  portal (future).

### 9.3 Mark integrity

```
canonical_mark = serde_json compact of, in this order:
  { v: 1, mark_id, worker_id, worker_run, employer_rut, type, server_ts, device_ts, offline,
    source, workplace_id, location: {lat, lon, accuracy_m} | null, prev_hash }
mark_hash     = hex(SHA-256(b"telemetry-mark-v1\0" ‖ canonical_mark))
prev_hash     = hash of the previous mark of the same worker, or 64 × "0" for the first one
```

- `server_ts` and `device_ts` are RFC 3339 UTC with second precision (`2026-10-11T12:00:05Z`).
- A correction never edits a mark: it is a new `correction` row that references the original and, once
  `ACCEPTED`/`CONSOLIDATED`, produces a new mark (source `CORRECTION`) in the chain. Reports show the
  effective value with the alteration marker (ATT-05).
- The agent recomputes the hash of every confirmed mark from the fields the server returned. A
  mismatch is shown, logged at `warn` (without personal data) and kept as evidence.
- The chain makes silent deletion or reordering detectable by anyone holding two receipts.

### 9.4 Worker app IPC

| Threat | Mitigation |
|:--|:--|
| Another local user's process talks to the service | Socket in a `0700` per-user dir; Windows pipe ACL for the current user only; per-start token file `0600` (SEC-18). |
| A process of the same user impersonates the UI | Same trust boundary as the user's session (it could also read the keystore while unlocked). The PIN still gates each mark. |
| UI compromised (XSS in WebView) | The UI holds no tokens or keys (PROC-03); CSP `default-src 'self'` with no `unsafe-eval`; the worst case is triggering actions the user could trigger, still PIN-gated for marks. |
| Malformed/huge frames | Length-prefixed frames ≤ 1 MiB, strict serde (`deny_unknown_fields`), version check (PROC-05). |

### 9.5 Logging (attendance)

Never at `info` or above: PIN (never anywhere), RUN, personal email, location, names. `info` may log
`mark queued type=WORKDAY_START offline=false` and counts.
